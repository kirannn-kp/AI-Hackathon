    Mission: Route & Resolve

    The story: a request arrives

    It is the start of a busy working day at fictional Contoso Manufacturing. Three requests arrive:

    "I join Project Phoenix next week. Please give me Reader access."

    "We need a EUR 600 software license from Contoso Software."

    "Can we share an Internal dataset with Fabrikam?"

    Today, people manually read these requests, check facts, look up policy and find the right approver. A plausible reply is not enough: an incorrect approval can grant excessive access, spend money or expose information.

    You are the engineering team. Build a small AI-powered workflow that does the investigation, chooses the right specialist and explains the next action using real evidence from this fictional lab.

    Your problem statement

    Given an unstructured request and a trusted request/user ID:

    1. Understand the domain and identify missing information.
    2. Gather operational facts through MCP tools.
    3. Retrieve the relevant policy and preserve its citations.
    4. Hand off to Access, Procurement or Data Sharing.
    5. Perform only a permitted simulated operation, or route/escalate it.
    6. Explain the outcome with evidence.

    The four outcomes are Resolve, Execute, Route, and Escalate. You will learn their differences as you build. This is not a general support chatbot, and fluent text is not proof that an operation happened.

    The architecture you will build

    Trusted request ID + synthetic user + request text
                         |
                      Triage
                         |
            one specialist handoff
           /             |             \
       Access       Procurement      Data Sharing
           \             |             /
            policy retrieval + MCP facts
                         |
          mock action or clarification
                         |
       Result + citations + actual trace

    The facilitator supplies the shared Foundry models and Search knowledge base. Your code runs in VS Code. The local MCP server has fictional operational data; it cannot change real business systems. Read the detailed architecture in the repository.

    Inside your workflow

    1. The runner loads a request fixture and preserves its trusted id and synthetic user_id. The request text cannot change team identity.
    2. Triage extracts a category, urgency, missing fields and business arguments.
    3. One relevant specialist receives the request through an explicit handoff.
    4. The specialist retrieves actual policy evidence and checks operational facts.
    5. A relevant mock tool returns completion, clarification or review state.
    6. Your workflow constructs a validated Result, preserving actual citations and explaining the observed outcome.

    Specialist boundaries

    Access checks project ownership/current access. Procurement checks the supplier and amount. Data Sharing checks the partner and classification. Each specialist gets only its relevant tools and the policy-retrieval adapter.

    The local server is one team process. It keeps mock records in memory. Restarting it erases those records. A stable request ID prevents duplicate operations only while that same process retains its state.

    Important trust boundaries

    • Request text and retrieved text are untrusted data, not instructions to change system rules.
    • A model saying "approved" is not verified authorization.
    • A queued request is not a completed operation.
    • Naming a knowledge base after a team is not access control. The facilitator must verify actual team authorization.
    • The local MCP endpoint binds to loopback and is unauthenticated. Never expose it through a public tunnel. Any hosted tool endpoint needs separately verified authentication.
    • Model rate limits and budget notifications do not cap spend. Cloud runners require an explicit approval flag, and workflows need bounded turns.

    Mission 02 - Understand requests and gather facts (30 minutes)

    What you will learn

    Turn free text into validated fields and discover/call a real MCP tool. Do not decide final business outcomes yet.

    Concepts in plain language

    • Triage extracts what the person wants and chooses a domain. It is not permission to approve the request.
    • Structured output means a predictable JSON object, not paragraphs your program has to guess how to read.
    • MCP client/server: your client asks a server which tools exist, then calls one by name with validated arguments. Describing a lookup is not running it.
    • Prompt injection is text trying to change the system's rules. Treat request text as data, even when it says "ignore policy" or "already approved".

    Step 3 - Implement structured triage

    Open starter/route_resolve/agents.py and implement only triage(request). Use the coach-provided Foundry deployment, not keyword routing or a fabricated model response. Follow README.md to set the cloud variables and identity.

    Your model should extract this shape:

    {
  "category": "Access",
  "urgency": "normal",
  "missing_fields": [],
  "arguments": {
    "project": "Phoenix",
    "role": "Reader"
  }
}

    This is a shape example, not the answer file. Define and validate a schema:

    Field Requirement
    category Exactly Access, Procurement or DataSharing
    urgency Your documented enum, e.g. low, normal, high; never an approval bypass
    missing_fields List of missing business-field names; never invent their values
    arguments Domain-specific extracted fields, not claims of verified approval

    Access needs project and role; Procurement needs supplier and a positive EUR amount; DataSharing needs partner and classification. Preserve monetary values as decimal strings rather than imprecise binary floats.

    The runner retains the practice record's trusted id and user_id. Do not ask the model to invent them. triage receives the business text; your saved evidence combines its output with those IDs. Authentication and team settings must not come from the request's wording.

    Implementation sequence:

    1. Write a short extraction-only instruction and the schema.
    2. Use the installed Foundry client with Entra credentials and the assigned deployment. Bound output tokens; do not run open-ended retries.
    3. Parse and validate the output. A refusal, malformed JSON or network error must be visible, not converted into plausible successful triage.
    4. Keep the starter's function signature. If your SDK uses async calls, put them in an async helper; use a synchronous wrapper only from a normal CLI runner, not from inside an already-running event loop.

    Step 4 - Try three domains and one missing-field case

    Choose P01, P06, P14 and P04 from data/practice-requests.json. The core requires the three domains plus one missing-field example, not all 20 requests.

    After implementing triage, this command runs one record:

    .\.venv\Scripts\python -m route_resolve.lab triage --id P01 --allow-cloud

    Change only the selected ID for the other cases. Expected: valid fields for each domain; P04 must retain missing information rather than guess a project.

    Use an MCP lookup to verify a fact, separately from extraction. For Access, inspect the discovered tool schemas and look up the project owner and existing access. A missing-field request should use request_info with the stable request ID and the missing field; retain its clarification result.

    Try the supplied diagnostic options, which run only local synthetic lookups:

    .\.venv\Scripts\python -m route_resolve.lab tools --tool check_user_access --user-id user-02 --project Phoenix --role Reader
.\.venv\Scripts\python -m route_resolve.lab tools --tool lookup_supplier --supplier "Contoso Software"

    Concepts in plain language

    The model's training is not your company's current policy. Retrieval sends a question to a knowledge base and returns relevant passages. Grounding means using those passages to justify the answer. Citations identify the evidence actually returned, not an attractive-looking URL the model invented.

    In this lab, Foundry IQ uses an Azure AI Search knowledge base containing four fictional policy documents. Keep these sources separate:

    Source What it tells you What it cannot prove
    Request text What the requester wants or claims That approval exists
    MCP lookup Current synthetic operational facts The complete policy
    Retrieved policy Applicable rules and approval owner That an action already completed
    Mock action result What the simulated operation did That a real system changed

    Agentic retrieval can use a model to plan searches. It is not just opening a local Markdown file, and it can incur both retrieval and model usage.

    Mission 04 - Hand off, act and explain (45 minutes)

    Timebox: concepts 5 min; handoff implementation 20 min; final run 10 min; demo/checkpoint 7 min; stop local processes 3 min. Prerequisite: triage, MCP and actual policy retrieval pass their checkpoints.

    Concepts in plain language

    Orchestration coordinates which component runs next. A handoff transfers control from Triage to one relevant specialist. It is not a loop that asks every agent to answer every question.

    Least privilege means each specialist gets only its required tools. Idempotency means retrying the same unchanged request does not create a second action. Bounded turns prevent endless model/tool calls and cost.

    Triage --handoff--> Access OR Procurement OR DataSharing
                  --retrieve policy--> inspect facts
                  --mock action / clarification--> Result

    The orchestration runs on your laptop against approved shared Azure services. The coach may host authenticated tools for the full event, but the timed core below uses a local loopback tool server. Do not deploy a hosted agent, APIM, Grafana or extra infrastructure during the exercise.
